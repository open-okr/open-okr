# MCP audit, 29 October 2026

Scope: the agent endpoint `/api/mcp` as an external agent meets it. Tools, toolsets, input schemas, prompts and errors.
Out of scope for this round: REST and OpenAPI, the interface, the OAuth flow, live behaviour (covered by the MCP UAT of 23 October).

Branch `agung`, commit `2182e303`. Static review of `contract/mcp.json`, `packages/core/src/api/mcp/*` and the specification. No live calls.

## 4. Corrections to the first review

The first review (same day) suggested moving `sessions.createBlocker` into `core`. That alone does not help: the tool needs a session id. See finding 10.

## 5. What is already right

- Errors set `isError` and name the refused fields (`dispatch.ts`, ZodError branch). A not-found stays not-found.
- Scope and the three hints agree on every tool, and a test pins them.
- Destructive tools are listed, not hidden, as `agent-surface.md` requires.
- No secret or workspace id in any tool schema. One grant is one workspace.
- Every tool has a generated example with its required fields.
- Goal reads return quality flags, so an agent sees the METHOD.md verdict.
- Every action is placed in a toolset, and `search` and `fetch` are always offered.

## 6. Generic advice not taken

| Skill advice | Why not |
|---|---|
| Snake_case tool names (`mcp-server-builder`) | The dotted names are the registry's own and shared with the CLI and REST. Raised as finding 14, not as a violation |
| A confirmation parameter on destructive tools (`mcp-server-builder`) | The specification uses a separate destructive scope and the client's approval prompt instead |
| Three to five objectives per level, check-ins every two weeks (`okr`) | METHOD.md sets the practice. A weekly rhythm is the canon here |

## 9. Is 394 tools too many?

The total is not what an agent pays for. A connection sees one or more toolsets, and the default `core` is 57 tools, about 8,300 tokens after `7360842e`. The question is whether each toolset holds only tools an agent can use.

| Toolset | Tools | Over a 128 cap | Tools that always answer `null` over MCP |
|---|---|---|---|
| `core` | 57 | No | 0 |
| `work` | 91 | No | 10 |
| `facilitation` | 115 | No | 6 |
| `admin` | 137 | Yes | 3 |
| `all` | 394 | Yes | 19 |

### 9.1 Finding 16 (RISK): AI-assist tools are listed but cannot work over MCP

`dispatch.ts` calls actions with no `drafter`, on purpose: `agent-surface.md` §5.1 says the MCP server makes no outbound AI calls. Each action that needs the drafter returns `null` when it is missing (for example `goal-assists.ts`, `draftObjective`).

Listed and always `null`: `goals.draftObjective`, `goals.rewriteKeyResult`, `goals.decomposeKeyResult`, `goals.suggestMeasure`, `goals.suggestParent`, `goals.draftRetrospective`, `goals.parseFilter`, `kpis.suggest`, `kpis.narrateTrend`, `comments.summarise`, `blockers.summarise`, `sessions.clusterRetro`, `sessions.draftMinutes`, `sessions.narrateDiagnostic`, `sessions.narrateDigest`, `imports.proposeMapping`, `copilot.availability`.

`agents.runCoach` and `agents.runChampion` also read the drafter but run deterministically without it, so they stay.

What goes wrong: the agent calls `goals.draftObjective`, gets `null`, and reports that drafting failed. The agent has its own model and should draft itself, then check the draft with the product's quality verdicts.

Fix: add the 17 to the "not for agents" list from `mcp-toolsets.md` §2.2. No registry or REST change.

### 9.2 Options for making it smaller

| Option | Tools removed from a connection | Cost | Recommendation |
|---|---|---|---|
| A. Drop the 17 AI-assist tools from the agent surface | 17 across `work`, `facilitation`, `admin` | One list, one test, `mcp-toolsets.md` | Do it |
| B. Move live-room session tools into a `room` toolset (votes, pulse, pass the mic, kudos, retro notes, stage notes) | About 30 to 40 from `facilitation` | Placement change, design doc update | Do it, after a person confirms which session tools a facilitator agent needs |
| C. Split `admin` into `admin` (people, roles, spaces, settings) and `integrations` (AI providers, channels, SSO) | `admin` from 134 to about 80 | Placement change | Do it, it clears finding 7 |
| D. Trim `core`: move `tokens.mine`, `tasks.move`, `people.orgChart` out | 3 | Small | Optional |
| E. Merge actions, for example one `settings` tool per area instead of read and update pairs | Many | Changes the registry, REST, CLI and every client. Breaking | No |
| F. Two meta-tools, `find_action` and `run_action` | All but two | Rejected in `mcp-toolsets.md` §4: the model loses typed schemas and the client cannot show what will run | No |

After A, B and C: `core` 57, `work` about 81, `facilitation` about 75, `admin` about 80, `integrations` about 50. Every toolset is under 128, and an agent that names `core,work` sees about 136 tools instead of 146, all of which work.

### 9.3 Answer

394 is the size of the product, not of a connection, and E and F show that shrinking the total costs more than it saves. The real problems are tools that are listed and cannot work (A), a facilitation toolset carrying the meeting room's buttons (B), and an admin toolset over the cap (C). Fix those three. Keep the total.

### 10.2 Details

**Q10. Blocker outside a session.** Confidence is asked at every check-in (§3.2), and the low band says "capture a blocker where something is actually blocked". §7.3 ties a blocker to an owner, a type, a next action and the next check-in, not to a session. Teams that check in asynchronously would otherwise wait up to a week. The `weekly-check-in` prompt should then ask for a next action at low confidence and a blocker where something is blocked.

**Q11. Publish a draft.** Publishing your own draft is the owner's act (§2.9), like `goals.create`, which is already in `core`. `approveDraft` is the reviewer's counterpart; without it a draft stalls in the inbox.

**Q12. Scope per tool.**

| Tool | Practice weight | Recommendation |
|---|---|---|
| `goals.close` | Routine (§8.8, §2.9 "Stop"). `goals.reopen` exists | `write`, with `closeReason` required |
| `cycles.close` | Writes the scorecard, feeds the next cycle (§8.9), affects every space, cannot be reopened. Correct a score with a written reason instead (§3.3) | `destructive` |
| `sessions.close` | Ends a meeting | `write` |
| `sessions.closeCommitments` | Weekly step (§7.2) | `write` |
| `people.suspend` | Removes all access; their champion and reviewer roles stay attached to someone who cannot act | `destructive` |

**Q13. The 70 session tools.**

| Group | Count | Tools |
|---|---|---|
| Facilitator agent: prepare, run remotely, follow up | 50 | create, bookCycle, open, advanceStage, skip, close, read, list, mine, participants, confirmConfidence, confidenceStatus, setNextAction, setWins, lowScores, createBlocker, resolveBlocker, reassignBlocker, blockerStatus, setCommitments, closeCommitments, carriedCommitments, confidenceTrend, listCommitments, setCoordinatorNote, postDigest, readStreak, digest, scoreKeyResult, setNarrative, narratives, setManagementAnswer, managementRetro, setRootCause, rootCauses, processHealth, recordDiagnostic, diagnostic, decideObjective, reset, captureLearning, addAction, completeAction, forward, minutes, scoringStatus, setTrend, setShifts, recordDecision, monthlyRecord |
| Live room, move to `room` | 14 | castVote, revealVotes, votes, addMinute, givePulse, roomPulse, revealObjectiveScore, passMic, giveKudos, addRetroNote, removeRetroNote, castRetroVote, submitProcessHealth, setStageNote |
| Unsure | 6 | narrateDigest, clusterRetro, narrateDiagnostic, draftMinutes (leave under finding 16), retro, recognition (`minutes` already carries them) |

The private vote and shared reveal exist so nobody anchors (§7.2, §8.3). `submitProcessHealth` is one person's anonymous answer (§8.5); an agent should not fill it in for someone.

**Q16. Checking quality without the AI tools.** The agent has its own model and can draft. What it cannot do is check a draft before it becomes real. `goals.read` returns only the score and failing check ids such as `OBJ-1`, not the prompt or the reason §4 gives each check, while the `review-against-the-canon` prompt asks the agent to quote the check as the product words it. Worse, the only way to test a draft is `goals.create`, and by default (§2.9) a mid-cycle objective goes live once it passes the block checks. Checking a draft publishes it.

**Q1. Rich text.** A check-in narrative is one or two lines (§7.2), a close reason one line (§8.8). Both are plain sentences. A check-in refused over formatting is a missed week.

### 10.3 Who uses the MCP surface in a normal week

| Persona | Through an agent each week | Toolset |
|---|---|---|
| Owner (champion) | What is due (`goals.due`), post check-ins, record values, comment, sometimes draft mid-cycle | `core` |
| Reviewer | Clear `review.inbox`, acknowledge one check-in per goal (§2.5) | `core` |
| Coordinator | Run the weekly session: low scores, next actions, blockers, commitments, digest (§7.2) | `facilitation` |
| Sponsor | Read escalations, the scorecard, `workflow.read`; record decisions in the monthly review (§7.5) | `core`, `facilitation` |
| Admin | Rarely through an agent. Irreversible acts need the destructive scope | `admin` |

### 10.4 Where the practitioner disagrees with this audit

1. Option B in §9.2 is smaller than estimated: 14 room-only tools, not 30 to 40.
2. Finding 12 first said closing "freezes" scores. METHOD.md does not say that. The reason is that `cycles.close` cannot be undone and feeds the next cycle. Corrected above.
3. Finding 10 overstated the cost: §7.3 is already session-neutral and the schema already allows a blocker with no session.
4. New, finding 17 (RISK): `goals.create` exposes `legacy` and `aiGenerated` to agents. `legacy` belongs to the importer; an agent that sets it could collide with import identity, unique on `(workspace_id, legacy_type, legacy_id)`.
5. New, finding 18 (RISK): the `weekly-check-in` prompt ignores the low band. At low confidence §3.2 requires a next action, and a blocker where something is blocked. The prompt asks for neither.
