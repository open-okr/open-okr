# Design review: KPI access (docs/design/kpi-access.md)

Reviewed on 19 November 2026 against commit `eed0082e` on `feat/0.10.0-designs`. Read only; every claim about code was checked by searching the repository.

**Verdict: not ready.** The direction matches Akmal's answers to G4-Q1 and G4-Q2. The design under it has false statements about today's code, no mechanism for the owner's grant authority, an import that skips almost every row, and most KPI read paths missing.

## Claims about today's code that are false

| # | Claim in the design | What the code says |
|---|---|---|
| F1 | "`full` (90)" in KA-D5, §6, AC-6 and §10 | `packages/core/src/access/levels.ts` defines `full: 100`. Line 10 of the design says 100, so it contradicts itself |
| F2 | KA-D2: the KPI context "sits under" the space or workspace context, so space bindings cascade | `access_contexts` (migration 0009) has no parent column. `resolveMemberAccessLevel` reads only the role plus bindings on that exact context. Goals reach their space by binding `space_standard` directly on the goal's context (`goals/service.ts` header) |
| F3 | `visibleResourceIds` pseudo-code (§5.2) | The real function takes `ids` and returns a `Set`, never `null`. `resolveBoundResourceIds` does not exist. Its role layer already joins `rp.domain = c.resource_type`, so no `case "kpi"` is needed once contexts exist |
| F4 | `can(actor, "kpis.read", subject)` (§5.3) | The real signature is `can(tx, {workspaceId, memberId, contextId}, level)`. There is no `kpis.read` action |
| F5 | Actions `kpis.get`, `kpis.records`, `kpis.delete` (§6) | They do not exist. Missing from the design: reads `kpis.grid`, `kpis.tree`, `kpis.spaceTrees`, `kpis.recoveryBoard`, `kpis.recoveryDraft`, `kpis.narrateTrend`, `kpis.suggest`; writes `kpis.deleteRecord`, `kpis.launchRecovery`, `kpis.recordResponse`, `kpis.createTree` |
| F6 | Screens S-23, S-24 and `/admin/import` (§7) | S-23 and S-24 are the Monthly and Quarterly review. The KPI screens are S-20 (grid), S-21 (detail), S-18 (tree). The route is `/admin/imports` (CSV wizard). The FlowyTeam importer is command line only (`pnpm import:flowyteam`) |
| F7 | The backfill calls `bindAgentsToContextInTx` (§3) | That function is in `packages/core`, which a data change in `packages/db` cannot import. Data change 0009 does the same work in raw SQL |
| F8 | A "system / importWorker" privilege and a "Migrator system actor" (§6, §8) | Neither exists. The importer runs as the human given with `--as`; CLAUDE.md says there is no ambient importer identity |
| F9 | `kpi_shares` is "completely unread" | `portability/policy.ts:762` and `people/export.ts:233` both name it |
| F10 | `kpis.shares` returns a grantor ID | `access_bindings` has no grantor column (`kpi_shares.created_by_id` does) |
| F11 | `SUBJECT_RESOLVERS` at `reads.ts:479` | It is at line 492 |

Confirmed true: the role matrix in `roles.ts`; `kpis.ts:483` creates a context only for KPIs with no space; no KPI action names a subject today; `unread.ts` lists `indicator_accesses`; TECHNICAL-PLAN lines 503, 529 and 542; the next data change is 0037; migration 0009 has RLS on the three access tables.

## Findings

| # | Severity | Problem | Fix |
|---|---|---|---|
| 1 | Blocker | KA-D5, §6: the KPI owner never gets `full`. `ownerMemberId` is a column, not a binding, so a Member owner resolves to 70 and "the owner may share" fails | Bind the owner's member group at `full` with a tag: on create, on owner change in `kpis.update` (unbind the old owner, bind the new one, as `reassignRoleInTx` does for goals), in the 0037 backfill, and in the importer |
| 2 | Blocker | Privilege escalation: `kpis.update` changes `ownerMemberId` at `edit`, so any Member, or a guest or Viewer with an `edit` share, can make themselves owner, gain `full` and share onward | Changing the owner requires `full` on the KPI. Add an acceptance criterion |
| 3 | Blocker | "Owner or Admin" does not match roles: workspace-roles.md §3 allows editing Admin and adding custom roles | State the rule as "`full` on the KPI: the owner binding, or a role granting manage on `kpi`", and confirm that wording with Akmal because it differs from what he approved |
| 4 | Blocker | §3 "No new DDL": `bindGroup` only raises, `unbindGroup` without a tag removes every binding of the group, and the untagged unique index allows one per group and context. A share and an owner binding collide, `unshare` removes the owner's grant, and lowering a share from edit to view does nothing | Add tags `owner` and `share` with an additive migration widening the `access_bindings.tag` check constraint (DATABASE.md and TECHNICAL-PLAN §4 in the same change). `kpis.share` sets a level; lowering is allowed for the `share` tag only |
| 5 | Blocker | Rolling upgrade: once single-KPI reads name the `kpi` subject, every space KPI with no context is not found until 0037 finishes; data changes run after deploy and Helm caps a run at 240 s | Either treat a missing context as the workspace context until the ledger says 0037 is complete, or ship contexts plus backfill in one release and enforcement in the next (PLAN §5.1). Add an acceptance criterion for a KPI with no context during the upgrade |
| 6 | Blocker | KA-D6: `people.importMember` creates placeholders, so "skip placeholder members" drops almost every share, and a placeholder has no role, so "covered by role" cannot be judged at import | Always write the binding for placeholders (it takes effect on claim). Report "covered by current role" as information, not a skip. Rewrite AC-7 |
| 7 | Blocker | Read paths missing (§6, §7, §9). Each reads every KPI today and must honour the KPI context, or the guest in AC-2 still sees everything: `kpis.grid` (also feeds `exports/lists.ts`), `kpis.list`, `kpis.tree`, `kpis.spaceTrees`, `kpis.recoveryBoard`, `kpis.recoveryDraft`, `kpis.narrateTrend`, `kpis.suggest`; search (`search/subjects.ts` sets `kpi: "workspace"` in `CONTEXT_FOR`, and `search_index.context_id` stores it, so existing rows need re-pointing in a data change); retrieval (`embeddings/governing.ts:332`); copilot (`copilot/read-tools.ts`, `fast-path.ts`); MCP (`api/mcp/research.ts`); the key result link (`kpis/linked.ts readLinkableKpi`); `webhooks/deliver.ts`, `nudges/message.ts`, `actions/review.ts`, `spaces.ts`, and the `kpi.created` activity payload. Today any member, guests included, can call `kpis.list` and `kpis.grid` with no check (`define.ts` skips enforcement at view); say so in §1 | Cover every path, and add one parity acceptance criterion per surface: a guest without a share gets nothing from search, copilot, MCP, export or the tree |
| 8 | Should fix | Agents and least privilege: 0037 binds the Coach and the Champion to every KPI context, so a space KPI becomes visible to an agent an admin unbound from that space | Bind agents only to spaceless KPIs (today's rule), or copy the space's agent bindings. `kpis.share` must refuse an agent as target and say what happens with placeholders. Decide whether `kpis.share` is on the agent surface; `kpis.importShare` gets `agentSurface: false` |
| 9 | Should fix | KA-D2: guests are invited per space and `space_standard` reaches only humans, so a space guest sees none of that space's KPIs | Ask Akmal whether space KPIs bind `space_standard` as goals do, and whether guests get anything |
| 10 | Should fix | Not addressed: does a share on a parent KPI cover its children; does a calculated KPI show to someone who cannot see its sources; a goal everyone can read shows a linked KPI's reading | Open questions decided silently: ask them |
| 11 | Should fix | Suspended members resolve to 0 and their bindings return on restore (state it, add acceptance criteria). Erasure must remove the member's share bindings. Say what happens to a KPI's context when the KPI or its space is soft deleted | As stated |
| 12 | Should fix | KA-D6 idempotency: `access_bindings` has no `legacy_id`, so a re-run silently restores a share an admin revoked after the import. `department_id` and `view_options = team` are not mapped or reported. The "visibility restriction" detection rule is undefined (reference §4.4 names no such flag). "Flag for review before import" is undefined. The `--only` domain is unnamed | Record the source key (audit row or ledger) and skip revoked ones; add a re-run criterion (second run writes 0). Map or report team shares. Define the detection rule from source columns. Say whether `--write` refuses without an override flag. Name the `--only` domain |
| 13 | Should fix | KA-D7 contradicts TECHNICAL-PLAN §4 line 160, which names `kpi_shares` as the home of narrow sharing, and TECHNICAL-PLAN outranks a design | Update TECHNICAL-PLAN §4, DATABASE.md, the portability policy and the people export in the same change, and record "bindings replace `kpi_shares`" as a decision to approve |
| 14 | Should fix | Audit (§8): rows come from the Operation spec with the human `--as` as actor, so `grantedBy` duplicates the actor. Does `kpis.share` notify the grantee (a new message kind needs asking)? The 0037 data change writes bindings with no audit row | State all three; accept the data change's missing audit row explicitly |
| 15 | Should fix | Contract and process: new actions need `pnpm gen:contract` (OpenAPI, CLI, MCP toolset placement), `subject: {type: "kpi"}` and `domain: "kpi"` on the writes, an in-handler `getAccessScoped` check (the floor is only a floor, per `operation.ts`), a changeset, catalogue keys in `en` and `ms` | Name these, and split the build into at least three commits: contexts and resolver, sharing, import |
| 16 | Nit | KA-D3, §5 and §7.2 say Viewers see only shared KPIs, but the Viewer role has `kpi: view`, so Viewers see every KPI | Only guests, or a custom role at 0, are narrowed |
| 17 | Nit | The status line "ready for design approved" reads as approved. Q3 should say a guest with one share could list members' names through `kpis.shares` | Write "awaiting design approved"; add the point to Q3 |
