# Design review: languages (docs/design/languages.md)

Reviewed on 19 November 2026 against commit `6ef6e541` on `feat/0.10.0-designs`. Read only; every claim about code was checked by searching the repository.

**Verdict: not ready.** Akmal's direction (L-Q1 to L-Q10) is covered. The design has a migration that does not work, several false claims about today's code, and no design for the machine-translation workflow or for how fonts and catalogues load per request.

## Claims about today's code that are false

| # | Claim in the design | What the code says |
|---|---|---|
| F1 | §5: the constraint is `workspace_members_language_check` | It is `workspace_members_language_known` (migration 0078, line 32) |
| F2 | §5.1: an old pod throws on an unknown code | Action outputs are not parsed at runtime (no `output.parse` in `packages/core/src/actions`). `resolveMemberLanguage` sees `ar`, finds it is not `en` or `ms`, and falls through to the workspace language (`member-language.ts:16-20`) |
| F3 | §4.3: term holes are `{term:objective}` | They are `{termObjective}` and `{termObjectiveLower}` (`terms.ts:20-23`) |
| F4 | §8: `intl-messageformat` is dependency-free and about 45 kB | 12.2.0 depends on `@formatjs/icu-messageformat-parser` and `@formatjs/fast-memoize` and unpacks to 117 kB (`npm view`) |
| F5 | §2 L-Q5: "measured image footprint" | Nothing was measured, and no Noto files exist in `apps/web/app/fonts` |
| F6 | §9: structural checks (character length bounds, baseline and target, timeframe) work in all locales | There are no character bounds. OBJ-2 counts words split on whitespace (`quality.ts:587`), so a Chinese objective counts as one word. KR-2 reads an English "from X to Y" pattern (`quality.ts:806`). `/\d/` matches ASCII digits only (`quality.ts:593,596`), so Arabic-Indic digits are not seen |
| F7 | §1, §9: which rules use word lists | OBJ-1 (output verbs, movement verbs, why markers, state words, end-state shape) and KR-5 (activity and impact nouns). KR-2 does not use the lists; it depends on language through its "from/to" parsing |
| F8 | Catalogue size 4,986 keys (nit) | 4,989 |

## Findings

| # | Severity | Problem | Fix |
|---|---|---|---|
| 1 | Blocker | §5 migration: `drop constraint if exists workspace_members_language_check` drops nothing, so the old `_known` constraint stays and rejects every new code | Drop `workspace_members_language_known` by its real name, keep `language is null or` explicit in the new check, update the Drizzle enum in `schema/workspaces.ts:113`, confirm 0172 is still free when the KPI access migration lands |
| 2 | Blocker | §5 rollout: "automated activation once old pods are drained" has no mechanism. Per F2 the real risks are: an old pod's account picker shows an `ar` member's value as blank; the old `updateMemberProfile` input enum (`people.ts:201`) refuses a save; a new pod could write before the migration runs | Restate the risk from F2. Then define the activation signal (for example a release marker row written once the rollout completes, with the test that proves it), or take L-Q2's fallback, a separate compatibility step, back to Akmal |
| 3 | Blocker | §3, §4: no machine-translation workflow. `missingKeys` fails the build when a locale lacks a key, so with ten locales every pull request that adds an English key fails unless nine translations come with it. Unsaid: which tool or provider translates and whether at build time or by hand; how the OKR glossary and term holes are protected; how a later key reaches the nine other files (a script plus a pending-translation ledger, or generation in the same pull request); how `SAME_IN_MALAY` generalises | Add a section and an acceptance criterion for the "new English key" path |
| 4 | Blocker | §4.2 catalogue load: `use-translations.tsx` is `"use client"` and imports `CATALOGUES`, so every browser downloads `en` (374 kB) and `ms` (399 kB); ten locales is about 4 MB. Passing the catalogue as a prop puts about 375 kB into the page data on every first load; a per-locale `import()` chunk avoids that. About 45 test files and `lib/translations.ts` read `CATALOGUES` synchronously. `translate` throws on a missing key, so a key used before its catalogue loads breaks the page | Choose the mechanism, state the bytes per first load per locale, keep a synchronous server API, and add an acceptance criterion that an English page ships only `en` |
| 5 | Blocker | §9 and L-Q8, the method: §2 and §9 present "excluded from the denominator, do not block strict mode or gates" as approved, but the plan says the detailed method change still needs approval. The skip is keyed on the member's locale, not the text, so a member who sets `de` and writes English skips OBJ-1 and KR-5: the language setting becomes a way past the gate. The structural checks are not language-neutral (F6). `quality.wordLists` is already a §11 parameter, so per-workspace lists are a cheaper option the design never weighs | Mark the §2 row as pending. Correct the list of structural checks. Ask Akmal how text language is detected (script or heuristic versus locale), and about OBJ-2's word count for Chinese, Arabic-Indic digits, and the §11 list option. Keep the proposed METHOD.md wording unapplied, as it is |
| 6 | Should fix | §7 fonts: "WOFF2 subset about 8 to 10 MB" is the whole font, and nothing says how English users avoid downloading it. Needed: slices (unicode-range), `preload: false`, loading tied to locale or content (Chinese titles in an English interface still need the fallback). `@react-pdf/renderer` (`render.tsx`) cannot read WOFF2, so PDFs need a TTF or OTF copy. Slicing needs a tool (for example fonttools), a build dependency to ask about. The air-gap `fonts-self-hosted` check looks only for one `next/font/local` import | A byte table for the browser (per locale and for English), the image and the PDF, plus an acceptance criterion for the English case |
| 7 | Should fix | §7.3 and AC-9, right-to-left PDFs: `@react-pdf/renderer` is not known to do bidirectional reordering, so AC-9 may need another library | A spike before approval, with a dependency question if it fails |
| 8 | Should fix | §6 right-to-left scope missing: an inventory (about 309 physical class uses such as `ml-`, `pr-`, `left-`, `text-left`, `border-l`, `rounded-l`, plus 59 `space-x`, `translate-x`, inline `left:` and arrow-key sites); a lint gate so physical classes do not return; Base UI's `DirectionProvider` (none in the repo), which menus, sliders and tabs need; `dir="auto"` on text inputs and the TipTap editor; `dir` in mail HTML (only `lang` today); translated board announcer text; a right-to-left pseudo-locale; running `s43` axe in `ar`. §6.4's "ArrowRight moves leftward in visual space" is backwards: arrow keys follow what the person sees | Add each item |
| 9 | Should fix | §3 conventions undecided: `en` listed as "MM/DD or DD/MM" (today's code uses `en-GB`); `ar` as "١٬٢٣٤ or 1,234" (the digit choice also decides number input parsing and how the method reads digits); `es` does not group 4-digit numbers. Hard-coded `"en-GB"` and `locale === "ms" ? "ms-MY" : "en-GB"` need a sweep: `activity/page.tsx:59`, `admin/ai/governance.tsx:247`, `admin/deleted/page.tsx:76`, `admin/channels/page.tsx:92`, `mail/account.ts:205` and more; keep `en-CA` where it formats ISO dates | Decide each convention and list the sweep |
| 10 | Should fix | Browser language matching: `browserLocale` (`accept-language.ts:80`) compares the primary subtag to the code, so `zh-CN` gives `zh`, never `zh-Hans`, and AC-3 fails. A naive fix would send `zh-TW` and `zh-Hant` readers to Simplified Chinese | Design the mapping (zh, zh-CN, zh-SG, zh-Hans to `zh-Hans`; Hant, TW, HK to the next fallback) and add an acceptance criterion |
| 11 | Should fix | L-Q1 signed-in fallback: `resolveMemberLanguage` falls back to `"en"`, not the instance default; the plan adds the instance step but the design never states it, and AC-2 uses an `en` instance so it cannot tell them apart | State the change and use a `de` instance in AC-2 |
| 12 | Should fix | §10 server text: "AI-off strings come from the UI catalogue" is impossible (`packages/core` cannot import `packages/ui`). Mail words are a separate English and Malay table (`mail/words.ts`), and notification templates are string builders. Unsaid: where server text lives and how its parity is tested; whether nudges and notifications store a key plus arguments or rendered text; generalising the `drafter.ts:367` English-or-Malay ternary; account mail has no per-user language, so a member who chose `ar` gets a password reset in the instance language | Answer each; raise account mail as a question |
| 13 | Should fix | §10 exports: "CSV columns remain English identifiers" contradicts plan L14 (headers in the requester's locale). `GOAL_COLUMNS` (`exports/lists.ts:129`) holds English labels such as "Objective" and "Progress %" | Decide whether CSV and XLSX headers are human-facing or machine-readable |
| 14 | Should fix | §8 ICU: correct F4; weigh precompiling messages to an AST at build time so no parser ships; cover apostrophe escaping (137 English messages contain `'`), term holes inside plural branches, migrating the 144 `...One`/`...Other` keys, and the 213 fragments in `fragmented-messages.ts` | As stated |
| 15 | Should fix | Contract: widening the `people.readMember` and `updateMemberProfile` enums changes `contract/openapi.json`, `cli.json` and `mcp.json`. The registry's `languageSchema` accepts any 2 to 35 character string today | Say `gen:contract` runs and a changeset is written; restrict new writes to the shipped list while tolerating unknown saved values |
| 16 | Should fix | §10 evaluation: `pnpm ai:evaluate` runs against the mock provider, which cannot prove a reply's language | Say what fixtures check per locale (script or language detection) and that the live check is a manual `--provider` run |
| 17 | Nit | Status line "ready for design approved" | Write "awaiting design approved" |
| 18 | Nit | The signed-out cookie `openokr_locale` is new | State its lifetime and attributes and whether the cookie notice covers it |
| 19 | Nit | Missing acceptance criteria | English first-load bytes (no CJK font, `en` catalogue only); a key added in English only; OBJ-2 on a Chinese title; Arabic-Indic digits in a key result; mixed-version test steps for finding 2 |

Correct in the design: the ten codes are valid BCP-47 tags; member, then workspace, then English is today's order (only the instance step is missing); migration 0172 is free (0171 is the last); member language is nullable and null means follow the workspace; the copilot already receives the member's locale (`copilot/answer.ts:278`); no dependency was added and METHOD.md was not edited.
