# PLAN.md

Architecture and delivery plan for `OpenOKR`, an open source OKR and work management platform.

Replace `OpenOKR` everywhere once the product is named. This file is the architecture authority for the repo. Product features live in REQUIREMENTS.md. Claude Code working rules live in CLAUDE.md.

---

## 1. What we are building

One codebase that ships as one product with three ways to run it:

1. **Zero-ops cloud.** A solo founder or small team deploys on Vercel plus Supabase (or Neon) in minutes. No devops person needed.
2. **Single server.** A small company runs one Docker Compose file on a cheap VPS or an office server.
3. **Enterprise.** A university or large organisation deploys the same version on their own Kubernetes with their own Postgres, SSO, backups and audit controls.

Same repo. Same release. Same behavior. The exact product modules (projects, strategy, operations and more) are defined in REQUIREMENTS.md, not here.

## 2. Non-negotiable principles

1. One codebase, one behavior, many runtimes.
2. Postgres is the only hard dependency. Everything else is optional or swappable.
3. No vendor SDK calls in core code. All runtime-sensitive capabilities sit behind adapters.
4. A small team can deploy in under 30 minutes. An enterprise can pass a security review.
5. Design first, then code. Claude Code writes design docs, a human approves, then it builds.
6. Secure by default: tenant isolation with RLS, MFA-capable auth, audit log from day one.
7. AI-native, not AI-dependent. AI is built into every module from day one as an accelerator over a complete manual path. It degrades to manual when disabled, can point at a local model for air-gapped installs, and every AI action runs inside the acting user's permissions. Full design in AI-NATIVE-PLAN.md.

## 3. License and governance

**Recommendation: AGPL-3.0 for the application code, plus a lightweight Contributor License Agreement (CLA).**

Why AGPL-3.0:

- It stops a third party from taking the code and selling a closed hosted version of it. Anyone who modifies it and offers it over a network must publish their changes.
- It is the proven license for exactly this category: Cal.com, Plane, Chatwoot and Grafana all ship under AGPL and still built strong communities and businesses.
- It is safe for the target buyers. A university or company that self-hosts for its own staff takes on no obligations. Obligations only trigger if they modify the code and serve it to outside users, and even then they only share those modifications.

Why a CLA on top:

- The business model is still open (see section 12). A CLA means the project owner keeps the right to dual-license, add a commercial `ee/` directory later, or run a paid cloud. Without a CLA, every contributor would have to approve any future license move.
- Use the CLA Assistant GitHub bot. Signing takes one click and does not scare contributors away.
- This is a one-way door. AGPL plus CLA can later relax to Apache-2.0 if adoption matters more than protection. Apache-2.0 can never tighten to AGPL for code already released.

Also do early:

- Register the product name as a trademark. The code is free, the brand is not. This is standard practice for open source companies.
- Add a `LICENSE` file (AGPL-3.0), a `CONTRIBUTING.md`, and a `GOVERNANCE.md` stating the project owner has final say while the project is young.

## 4. Architecture in one page

A **Next.js (App Router) modular monolith** inside a Turborepo workspace.

```
apps/
  web/                 Next.js app: UI, tRPC API, REST API
packages/
  core/                Domain logic and services. Framework-free.
  db/                  Drizzle schema, migrations, RLS policies
  adapters/            Ports and drivers (see table below)
  ui/                  Shared shadcn/ui components (Base UI primitives, not Radix; SmoothUI/Motion for animation)
  config/              Shared tsconfig, lint, env schema
deploy/
  docker/              Dockerfile, docker-compose.yml, Caddy config
  helm/                Helm chart for Kubernetes
  vercel/              Vercel deploy notes and env template
docs/
  design/              Generated by Claude Code from REQUIREMENTS.md
```

### Runtime profiles

One env var selects the profile at boot: `RUNTIME=container` or `RUNTIME=serverless`. Feature code never checks this var. Only the adapter loader does.

### Adapter ports and drivers

| Port | Container driver (default) | Serverless driver (Vercel) |
|---|---|---|
| JobQueue | pg-boss (in Postgres) | Inngest (or Trigger.dev / QStash) |
| Realtime | WebSocket server + Postgres LISTEN/NOTIFY | Supabase Realtime (or Pusher / Ably) |
| FileStorage | Local disk or MinIO (S3 API) | Supabase Storage or S3 / R2 |
| Mailer | SMTP | Resend (or SMTP) |
| Cache and rate limit | In-process + Postgres | Upstash Redis (optional) |
| Search | Postgres full-text search | Postgres full-text search |
| AIProvider | Anthropic / OpenAI / Google / OpenRouter / Ollama | Same |

Rules that make this real:

- Vendor SDKs are imported only inside `packages/adapters`. Nowhere else.
- Feature code calls `jobs.enqueue(...)`, `realtime.publish(...)`, `storage.put(...)`. It never knows which driver is running.
- CI runs the full test suite against **both** profiles. That is what keeps "one codebase" honest.
- AI is native to the product but never on a required path (AI-NATIVE-PLAN.md). Unlike the other ports, the AIProvider driver is selected by **stored config** (a deployment, workspace, or per-user bring-your-own key), not the `RUNTIME` var. It is on by default wherever a provider is configured, per feature; a deployment with no key behaves as AI-off. Air-gapped installs point the AIProvider at Ollama or a local OpenAI-compatible endpoint, or disable it. OpenOKR also **ships an MCP server** so external AI agents act as the user, within the user's permissions. No core flow may require an LLM.

### Multi-tenancy

- Top-level unit is a **workspace** (an organisation). Every business table carries `workspace_id`.
- Postgres Row Level Security enforces isolation on every table, in the same migration that creates the table.
- One deployment can host one workspace (a university's own install) or thousands (a future hosted cloud). Same schema either way.

## 5. Deployment tiers

| Tier | Who | Stack | Setup effort | Realistic monthly cost |
|---|---|---|---|---|
| Zero-ops cloud | Solo, small team | Vercel + Supabase or Neon | Deploy button + env vars, ~15 min | $0 to evaluate. About $45 for a small business (Vercel Pro $20 per seat + Supabase Pro $25). Note: Vercel's free Hobby plan is for non-commercial use only. |
| Single server | SMB, budget-minded, privacy-minded | Docker Compose: app + Postgres + Caddy (+ MinIO optional) | ~30 min on any VPS | $10 to $20 VPS |
| Enterprise | University, large org | Helm chart on their Kubernetes, external Postgres, SSO, backups | Their platform team, hours not weeks | Their infrastructure |

All three run the same tagged release. Publish signed Docker images to GHCR on every release.

## 6. Security model

- **Authentication:** Better Auth. Email + password, passkeys, TOTP MFA. SSO via OIDC and SAML ships in the open core because institutions will not adopt without it (see decision register for the final call). SCIM provisioning comes in the enterprise phase.
- **Authorisation:** role-based access control checked in `packages/core`, with RLS as the database backstop. Roles are configurable data (permissions attached per role), not a fixed enum; the seeded defaults are **Owner, Project admin, Member, Reader** plus the builtin **Non-member** and **Anonymous** pseudo-roles (see TECHNICAL-PLAN.md §4.1 and IMPLEMENTATION-PLAN.md P2-T01). Never rely on the UI to hide things.
- **Audit log:** an append-only `audit_events` table from day one. Cheap to build early, painful to retrofit, loved by enterprise reviewers.
- **Input:** every external boundary validated with Zod.
- **Supply chain:** Dependabot, CodeQL, pinned lockfile, signed images, SBOM attached to releases.
- **Secrets:** env vars only. Document Vault integration for enterprises. Never commit secrets, never log them.
- **Headers:** strict CSP, secure cookies, rate limiting through the adapter.

## 7. Realtime: live now, co-edit ready

Ship now:

- Presence (who is viewing this page).
- Live lists and dashboards (a record changes, every open screen updates).
- In-app notifications.

All through the Realtime port with channel semantics: `realtime.subscribe(channel)`, `realtime.publish(channel, event)`. Channels are named per entity, for example `workspace:{id}:project:{id}`.

Design rules that make CRDT co-editing a bolt-on later, not a rewrite:

1. Document-like content is stored as structured JSON with a `version` column, never as opaque blobs scattered across columns.
2. All writes go through one server mutation layer. A future Yjs sync server becomes an alternative write path into the same layer.
3. Optimistic UI with conflict handling: a stale write returns 409 and the client refetches. No silent last-write-wins on rich content.
4. Presence exists from day one, so the collaborative feel and the UI affordances are already there when co-editing lands.

When co-editing ships, it will be Yjs with a sync server running as another adapter driver (Hocuspocus in the container profile, a hosted equivalent in serverless). Nothing before that point may assume a single editor.

## 8. Data and AI

- Drizzle migrations, forward-only, committed with the feature that needs them.
- A seed script that creates a demo workspace with realistic data. This powers the public demo instance and local dev.
- AI is a first-class domain, specified in AI-NATIVE-PLAN.md. The AIProvider port exposes chat, streaming, tool-calling, embed, and extract. Providers include Anthropic, OpenAI, Google, OpenRouter, and local models (Ollama, any OpenAI-compatible endpoint). Keys are brought at the deployment, workspace, or individual-user level and encrypted at rest. AI appears in every module as opt-out-able assists, an in-app copilot that acts inside the user's permissions, and an MCP server that lets any AI agent drive OKRs and projects. Every AI action is permission-checked, metered, capped, and audited; none sits on a required path. Semantic search uses the pgvector extension of Postgres, so no new service is required.

## 9. Quality, CI and releases

- Vitest for unit and integration tests. Playwright for end-to-end.
- Biome for lint and format (one fast tool).
- Type checking with `tsc --noEmit` in strict mode.
- CI matrix: the suite runs under `RUNTIME=container` and `RUNTIME=serverless` on every PR.
- Releases via Changesets: version, changelog, tagged Docker image, GitHub release. Enterprises pin versions; never force silent upgrades.
- Observability: OpenTelemetry instrumentation with self-hostable backends (Grafana stack, self-hosted Sentry), because on-prem customers cannot ship telemetry to SaaS tools. Telemetry is opt-in and documented.

## 10. Delivery phases

Eight sequential phases; each gates on the one before it.

**Phase 1, prove the pipeline (roughly week 1).**
Repo scaffold, CI, adapter interfaces with both driver sets, Better Auth, workspaces, RLS, and a hello dashboard deployed to all three targets. No product features yet. If the walking skeleton runs on Vercel, on Compose and on Helm, everything after is feature work.

**Phase 2, core platform.**
RBAC, audit log, notifications, file uploads, workspace settings, invitations, the importer skeleton, and the app shell / design system.

**Phase 3, work management.**
The execution pillar, built from REQUIREMENTS.md. Claude Code writes the design docs first (see CLAUDE.md), a human approves, then it builds in vertical slices: schema + RLS + API + UI + tests per slice — work packages, queries, gantt, boards, wiki, meetings, time/cost, and the source-1 importer.

**Phase 4, strategy modules (OKR / KPI / check-ins / tasks).**
The namesake surface: OKR cycles, objectives and key results with a pure scoring engine, KPIs with per-period records and calculated formulas, check-ins, the scorecard, and the FlowyTeam importer. Tasks unify into work packages (built in Phase 3). Schema in TECHNICAL-PLAN.md §4.12; tasks in IMPLEMENTATION-PLAN.md Phase 4.

**Phase 5, the AI layer.**
The provider abstraction with bring-your-own-key and local-model support, the admin AI console, usage/cost metering and caps, the permission-checked tool registry, the in-app copilot, embeddings/RAG, the MCP server, and the per-module assists (OKR authoring; work packages, meetings, wiki). Detail in AI-NATIVE-PLAN.md.

**Phase 6, hardening.**
Performance budgets, backup and restore documentation, observability dashboards, load testing at university scale (thousands of users, one workspace), security review, accessibility audit, and the cutover rehearsal.

**Phase 7, enterprise pack.**
SSO, LDAP/SCIM, 2FA, audit export, advanced Helm values, air-gap install guide, upgrade playbooks.

**Phase 8, community launch.**
Docs site, one-click deploy buttons, hosted demo instance, CONTRIBUTING guide, good-first-issues, launch posts, methodology template gallery.

## 11. Working with Claude Code

The loop this repo is built for:

1. Human fills REQUIREMENTS.md.
2. Claude Code reads CLAUDE.md (automatic), PLAN.md and REQUIREMENTS.md, then generates `docs/design/`.
3. Human reviews and approves the design docs.
4. Claude Code scaffolds Phase 1, then builds features slice by slice.
5. Every feature meets the definition of done in CLAUDE.md before it merges.
