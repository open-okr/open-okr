## 1. Goals & OKR model (targets, check-ins, progress, alignment, timeframes)

### [CRITICAL] No cadence/staleness engine: objective status has no 'outdated/overdue' dimension

*plan status: `missing`*

- **Operately today:** Operately tracks per-goal next_update_scheduled_at, advances it on each published check-in (Operately.Time.calculate_next_monthly/weekly_check_in), and derives an 'outdated' status when a check-in is missed by >3 days (Operately.Goals.outdated?/1), which sits in the status priority cascade (Goal.status/1) ABOVE the last confidence value. A never-scheduled goal counts as outdated.
- **Evidence:** Plan: TECHNICAL-PLAN §6.2 step 5 derives status ONLY from confidence buckets (9-10 completed / 5-8 on track / 1-4 at risk / else not tracked); §4.12.3 objectives table has NO next_check_in_at / staleness column; cadence lives only on okr_cycles (§4.12.2) and check_in_sessions are per-user period rows (§4.12.5). Yet IMPLEMENTATION-PLAN P4-T14 line 761 fires a notification for KRs 'confidence 1-4 or overdue' — so 'overdue' is referenced but never defined in the schema or status model. Operately: goal.ex Goal.status/1 + goals.ex outdated?/1.
- **Recommendation:** Add a per-objective next_check_in_at (advanced by cadence math honoring workspace timezone) and an 'outdated' status that the scoring engine (§6.2 step 5) emits when the scheduled check-in is missed beyond a configurable grace window; wire it above confidence in the status cascade. Define what 'overdue' in P4-T14 actually reads from.

### [HIGH] No explicit objective close lifecycle (achieved/missed outcome + retrospective + reopen)

*plan status: `missing`*

- **Operately today:** Operately closes a goal with an explicit success flag + success_status (:achieved/:missed) and attaches a retrospective (GoalClosing.run/3 writes a goal_closing activity + a CommentThread), plus a full reopening path that clears closed_at/closed_by/success/success_status (GoalReopening). success_status is the TOP of the status cascade.
- **Evidence:** Plan: objective 'status' includes 'completed' but it is derived purely from confidence >=9 (TECHNICAL-PLAN §6.2 step 5 / §4.12.3), so an objective is 'done' only if someone set confidence to 9-10 — there is no explicit close action, no achieved-vs-missed distinction, no per-objective retrospective, and no reopen. Closing exists only at the cycle level (OVERVIEW §4.5 archive-to-snapshot; IMPLEMENTATION-PLAN P4-T11). Operately: goal.ex closed_at/success/success_status, GoalClosing/GoalReopening, Goals.Retrospective.find/1.
- **Recommendation:** Add closed_at/closed_by_id/success_status(achieved|missed) columns to objectives, a close/reopen action with a retrospective (reuse comments/§4.6 like discussions), and put success_status at the top of the §6.2 status derivation. Distinguish 'ended by cycle' from 'explicitly achieved/missed'.

### [HIGH] No unified cross-pillar work map (objectives + sub-objectives + projects + work packages in one tree)

*plan status: `missing`*

- **Operately today:** Operately's WorkMap (WorkMaps.WorkMap / GetWorkMapQuery / WorkMapItem behaviour) renders goals, sub-goals, projects and tasks in one hierarchical, view-access-filtered tree, each row exposing computed status/state/progress/next_step, owner, privacy and assignees, with space/parent/champion/reviewer/contributor filters. This is the literal embodiment of 'strategy + execution in one place'.
- **Evidence:** Plan headline thesis is exactly this join (OVERVIEW §L18 'They meet at the level where work happens'; work_packages.objective_id/key_result_id/kpi_id, TECHNICAL-PLAN §4.12.7). But the UI is split: S-16 OKR explorer + S-18 alignment diagram (UIUX-PLAN L141/IMPLEMENTATION P4-T06) show only objectives/KRs; work packages live in separate tables/boards/gantt. No single navigable tree nests objectives -> sub-objectives -> linked projects -> work packages with rolled-up status/next-step. Operately: work_maps subsystem + Goal WorkMapItem callbacks.
- **Recommendation:** Specify a unified Work Map view (new UIUX screen + a query that merges objectives, child objectives, and linked work_packages into one hierarchy with computed status/progress/next_step) as a P0/P1 deliverable in Phase 4; this is a chance to BEAT Operately by including full work packages/gantt, not just lightweight tasks.

### [HIGH] Two-role ownership (champion + reviewer) and per-check-in acknowledgement workflow are absent

*plan status: `underspecified`*

- **Operately today:** Operately goals have a distinct champion AND reviewer (two-role ownership with atomic access rebinding on change), and a real acknowledgement workflow: the reviewer acknowledges the champion's check-in (and vice versa), stamping acknowledged_at/by and updating the acknowledger's assignment count/inbox (GoalUpdateAcknowledging, update/permissions.ex).
- **Evidence:** Plan: objectives/KRs carry a single lead_id? (TECHNICAL-PLAN §4.12.3) and check-ins get a session-level check_in_reviews row with submitted/body (§4.12.5) — a manager review of a whole session, not a distinct reviewer role per objective nor an acknowledge action on an individual check-in tied to an inbox assignment. Operately: goal.ex champion_id/reviewer_id, GoalUpdateAcknowledging.run/2.
- **Recommendation:** Add a reviewer_id distinct from lead/owner on objectives, an acknowledge action + acknowledged_at/by on check_ins, and wire acknowledgement into the notifications/inbox (P4-T14) as an assignment. Specify access rebinding when champion/reviewer changes.

### [MEDIUM] Check-in snapshots are per-subject values, not immutable point-in-time bundles with diffs; no draft check-ins

*plan status: `underspecified`*

- **Operately today:** Each Operately check-in embeds an immutable snapshot of ALL targets (with previous_value for diffing) and checklist state at post time (update.ex embeds_many targets/checks), supports draft->publish with four side-effect short-circuits (no goal pointer / target write / checklist write / activity until published) and a published->draft guard, plus time-boxed full edits (3 days AND latest only) and pointer rollback on deletion.
- **Evidence:** Plan: check_ins is one polymorphic row per objective/KR with value/confidence/progress/remark/category (TECHNICAL-PLAN §4.12.5) plus key_result_values history (§4.12.3); OVERVIEW §4.4 says 'kept as a dated snapshot' but there is no full-objective bundle with previous_value diffs, no draft/published state on a check-in (only session.submitted bool), no edit-window or delete-rollback rules. Operately: update.ex, GoalCheckIn/GoalCheckInEdit/GoalCheckInDeleting.
- **Recommendation:** Specify a check-in as an immutable snapshot bundle (all KR values + previous_value + confidence at that instant) to power a diff view; add draft/published state + published_at with side-effect suppression, an edit window, and pointer rollback on delete.

### [MEDIUM] Objectives locked to a shared rigid cycle; no flexible per-objective timeframe

*plan status: `underspecified`*

- **Operately today:** Operately goals carry their own flexible contextual timeframe at day/month/quarter/year granularity with validated human labels ('Q3 2025','Jul 2025') and helpers for current/next quarter etc. — NOT locked to a single org-wide cadence (contextual_dates/timeframe.ex).
- **Evidence:** Plan: every objective must belong to an okr_cycle with a single workspace default_cadence (TECHNICAL-PLAN §4.12.2/§4.12.3 cycle_id NOT NULL implied; OVERVIEW §4.2 'switch the active cycle from a single control'). A 6-week objective, a custom date range, or objectives on differing horizons in the same period cannot be expressed. Operately: goal.ex embeds_one timeframe.
- **Recommendation:** Allow an optional per-objective timeframe override (contextual start/end + granularity) that defaults to the cycle bounds; keep the cycle as the grouping default but not a hard constraint. Note this as a superiority lever over Operately (validated labels + engine-aware).

### [LOW] Goal discussions and per-goal privacy levels are thin vs Operately

*plan status: `underspecified`*

- **Operately today:** Operately supports free-form TITLED discussion threads on a goal (distinct from check-in comments) and derives 4 privacy levels (public/internal/confidential/secret) from per-goal access bindings plus explicit per-person membership add/update/remove and a company read-only mode.
- **Evidence:** Plan: discussions 'reuse the comments table with subject_type' (TECHNICAL-PLAN §4.12.5) — no titled thread concept; access is RLS + RBAC strings + objective_shares me/manager/team/everyone (§4.12.8) with no named privacy tiers or per-person membership UI for a single objective. Operately: GoalDiscussionCreation (titled CommentThread), Goals.Permissions calc_privacy, ListAccessMembers.
- **Recommendation:** Add titled discussion threads on objectives and a named per-objective privacy level derived from shares/RLS, with a per-person access-member UI; confirm audit_events capture old->new on every OKR field edit.

**Ways to be superior (beyond parity):**

- _(M)_ **Predictive RAG from KR value trajectory, not just current confidence** - Use the key_result_values history (already planned, §4.12.3) so the scoring engine projects end-of-cycle attainment from the value slope and flags 'trending off-track' BEFORE confidence/RAG turns red. Surface a mini sparkline + forecast per KR. _Why:_ Operately's status is reactive: it only reflects the latest human-entered confidence plus a fixed 3-day outdated grace. A trajectory forecast catches drift Operately can't show.
- _(M)_ **pgvector-powered alignment & duplicate-objective detection** - Embed objective/KR text (AI domain S embeddings) and suggest the best parent objective/KR when aligning, and warn when two teams write near-duplicate or conflicting objectives across the org. _Why:_ Operately's alignment is a manual recursive-CTE parent picker with no semantic help or overlap detection; the plan's pgvector + AI-native stack makes this cheap.
- _(M)_ **RLS-enforced per-objective privacy (DB-level, not app-level bindings)** - Implement the named privacy tiers via Row Level Security predicates keyed on app.workspace_id + share rows, so confidential objectives are unreadable even on a raw query. _Why:_ Operately enforces goal privacy in the application layer (Access.Binding thresholds in can_view); a leaked query path bypasses it. RLS closes that class of bug entirely.
- _(S)_ **Configurable staleness grace per cadence + AI check-in nudge** - Make the 'outdated' grace window configurable in performance_settings per cadence, and have the copilot draft the overdue check-in (pre-filled values from linked work-package completion) for one-click confirm. _Why:_ Operately hardcodes a 3-day grace and has no AI-assisted check-in drafting; the plan's cadence data + copilot make both trivial.
- _(S)_ **AI-drafted retrospectives and cycle summaries from check-in history** - On objective close / cycle archive, generate a draft retrospective and a cross-cycle confidence-trend narrative from the check-in and value history, with human edit-before-save (matches the plan's confirm-before-write AI rule). _Why:_ Operately's retrospective is a manual free-text thread; the plan already stores richer per-period history to summarize.
- _(M)_ **Full versioned objective snapshot + visual diff timeline** - Store each check-in as an immutable snapshot of the whole objective (all KRs + previous_value + confidence + timeframe) and render a scrubber/diff timeline showing exactly what moved between check-ins. _Why:_ Operately snapshots targets per check-in but exposes no first-class diff-timeline UI; making it a headline feature turns a hidden data structure into a differentiator.

**Exact plan edits:**

Missing next_check_in_at, closed_at/closed_by_id/success_status(achieved|missed), reviewer_id (distinct from lead_id), and an optional per-objective timeframe override. -> **Fix:** Add columns: reviewer_id?, next_check_in_at (timestamptz), closed_at/closed_by_id, success_status enum (achieved|missed), and an optional contextual timeframe (start/end + granularity) that defaults to cycle bounds. Add 'outdated' and 'closed' to the derived status enum.

- **UIUX-PLAN.md (add screen) + IMPLEMENTATION-PLAN.md Phase 4** - The OKR explorer (S-16) and work-package tables/boards/gantt are separate; the product's core thesis 'strategy + execution in one place' (OVERVIEW §L18) has no unified navigable view. -> **Fix:** Add a Unified Work Map screen and a merged query nesting objectives -> sub-objectives -> linked projects -> work packages with computed status/progress/next_step and space/owner/reviewer filters; add a Phase 4 task for it.

## 2. Projects, milestones, tasks, project check-ins, retrospectives, timeline

### [CRITICAL] No project-level check-ins, health status, or operating cadence — OpenOKR only check-ins OKRs

*plan status: `missing`*

- **Operately today:** Operately's core operating rhythm: weekly project check-ins carrying a health status (on_track/caution/off_track) + rich body, draft/publish state machine, reviewer acknowledgement, and automatic cadence rescheduling (next Friday) with an 'outdated' flag when >3 days overdue (check_in.ex, project_check_in*.ex, Operately.Time, outdated?/1).
- **Evidence:** OpenOKR: REQUIREMENTS §3 'Module: Check-ins (P1)' and DATABASE §check_ins define check_ins with subject_type ('objective'/'key_result') ONLY; TECHNICAL-PLAN §4.12.5 scopes check-ins to OKR/KR. Projects (DATABASE line 195-196) carry only a free-text `status` + `status_explanation` with no cadence, no health enum, no acknowledgement, no overdue detection. Operately: check_in.ex draft/published + acknowledged_by/at; Projects.outdated?/1 3-day grace; Time.calculate_next_weekly_check_in.
- **Recommendation:** Add a first-class project (work-container) check-in entity distinct from OKR check-ins: fields status/health enum, rich body, state (draft/published), acknowledged_by/at, next_check_in_scheduled_at with a tolerance-window cadence engine, and a derived `outdated` flag with grace period. Spec it in REQUIREMENTS (promote to P0), DATABASE (domain C), and IMPLEMENTATION Phase 3. Model acknowledgement so a designated reviewer must sign off.

### [HIGH] No retrospectives — closing a project captures no structured learning

*plan status: `missing`*

- **Operately today:** Operately requires a retrospective (rich content) to close a project; retrospectives are separately editable and editing can change the project's success_status (retrospective.ex, project_closed.ex, project_retrospective_editing.ex).
- **Evidence:** OpenOKR plan has no retrospective concept anywhere (grep across REQUIREMENTS/TECHNICAL/DATABASE/IMPLEMENTATION finds none for projects; the only 'retrospective' mentions are prose about time/cost data). Project close is just P3-T01 CRUD setting `status`/`archived`.
- **Recommendation:** Add a `project_retrospectives` table (project_id, content rich, success/outcome) and a close flow that requires (or strongly prompts) a retrospective plus a success_status (achieved/missed). Wire into IMPLEMENTATION Phase 3 project lifecycle and the activity feed. This is a natural AI-assist surface (auto-draft retro from check-in history).

### [HIGH] No champion/reviewer accountability model on projects

*plan status: `missing`*

- **Operately today:** Operately projects have explicit contributor roles — champion, reviewer, contributor — each with responsibility text and kept in lockstep with access bindings (full_access for champion/reviewer). Reviewer is the person who acknowledges check-ins; champion is the accountable owner. Person-swap logic correctly downgrades outgoing holders (contributor.ex, project_contributor_edited.ex).
- **Evidence:** OpenOKR uses generic OpenProject-style membership: work_packages have `assignee_id` + `responsible_id` and projects rely on RBAC roles (DATABASE §work_packages, §roles). There is no accountable-owner/reviewer distinction at the project level and no acknowledgement authority tied to a role.
- **Recommendation:** Add a `project_contributors` concept (or extend memberships) with champion/reviewer/contributor roles and per-role access levels, migrated in lockstep with RLS/access grants. Define reviewer as the acknowledger for the new project check-in. Add to REQUIREMENTS Projects module and DATABASE domain C.

### [HIGH] Single assignee per work package — regression vs Operately's multiple assignees

*plan status: `underspecified`*

- **Operately today:** Operately tasks support multiple assignees (task_assignees many-to-many) and auto-add each assignee as an edit-access contributor.
- **Evidence:** OpenOKR work_packages have a single `assignee_id` (TECHNICAL-PLAN §4.3 line 80; DATABASE §work_packages line 232) and the FlowyTeam importer explicitly maps 'single assignee' (IMPLEMENTATION P4-T16, line 743). This is the OpenProject model and is strictly weaker than Operately.
- **Recommendation:** Either make `assignee_id` a `work_package_assignees` join table, or add a documented multi-assignee capability with a designated primary. Update DATABASE domain D, TECHNICAL §4.3, and the inline-edit/board specs in UIUX. Keep single-assignee import mapping but allow >1 going forward.

### [MEDIUM] Milestones are thin 'versions', not rich work objects

*plan status: `underspecified`*

- **Operately today:** Operately milestones are first-class: contextual-date timeframes, a phase enum (concept/planning/execution/control), descriptions, comment threads, per-milestone task kanban boards + task ordering, completion via a comment-with-action, and a computed project 'next step' (earliest-due pending milestone) (milestone.ex, ordering_state.ex, CreateMilestoneCommentOperation).
- **Evidence:** OpenOKR models milestones as OpenProject `versions` (DATABASE §versions: name/status open-locked-closed/sharing/start/effective_date) plus optionally a work_package of an is_milestone type (DATABASE §types). No comment thread, no per-milestone board, no phase, no computed next-step. UIUX gantt only draws 'milestone diamonds'.
- **Recommendation:** Enrich the milestone concept: add comment threads (already polymorphic — just enable on versions), a project 'next step' derived field (earliest-due open milestone with a documented tie-break), and optionally a milestone-scoped board view. Add to REQUIREMENTS Projects & versions and UIUX. Consider a phase/stage field to align with the P2 phases/gates module.

### [MEDIUM] Reminders are absolute-time only; no due-relative reminders

*plan status: `underspecified`*

- **Operately today:** Operately per-task reminders are configurable and due-relative (before_due/due_day/overdue/on_date); relative reminders are rejected without a due date and auto-stripped when the due date is removed (reminder.ex, update_due_date_attrs).
- **Evidence:** OpenOKR `reminders` table is (work_package_id, user_id, remind_at, note) — a single absolute timestamp (TECHNICAL-PLAN §4.7 line 138). 'Date alerts' are a separate P1 notification-settings scaffold. No relative-to-due-date reminder type and no cleanup rule.
- **Recommendation:** Extend `reminders` with a `kind` (on_date/before_due/on_due/overdue) and offset, validate that relative kinds require a due date, and strip them when the due date is cleared. Note this in TECHNICAL §4.7 and the notifications implementation task.

### [MEDIUM] No unified cross-cutting work-map / hierarchy view spanning goals + projects + tasks

*plan status: `underspecified`*

- **Operately today:** Operately's WorkMapItem behaviour lets goals, projects, and tasks expose a common status/state/next_step/progress and compose into one hierarchy/work-map view with a deliberate status layering (success_status > paused > outdated > last-check-in > pending).
- **Evidence:** OpenOKR links work_packages to objectives/KRs/KPIs (DATABASE §work_packages link columns) and offers 'My work' tabs + dashboards/portfolio (UIUX §sidebar, REQUIREMENTS dashboards P1), but there is no single view that renders the whole goal->project->task tree with a uniform derived status/next-step per node. The strategy 'Alignment' view is OKR-only.
- **Recommendation:** Specify a work-map view and a shared derived-status contract (status/state/next_step/progress) computed by a job across objectives, projects, and work packages. Add to UIUX and REQUIREMENTS; it is a strong differentiator and pairs with the pgvector/AI narrative layer.

### [MEDIUM] Project lifecycle lacks pause/resume and explicit success outcome

*plan status: `underspecified`*

- **Operately today:** Operately projects support active->paused->resumed (resume writes a comment thread and reschedules the next check-in) and active->closed with a success_status (achieved/missed); status is derived, not just a stored string (project.ex state/1 & status/1, project_pausing/resuming/closed.ex).
- **Evidence:** OpenOKR projects have a single free-text `status` + `archived` bool set via P3-T01 CRUD (DATABASE line 193-196; IMPLEMENTATION P3-T01). No pause/resume semantics, no success/outcome field, no derived status precedence.
- **Recommendation:** Define an explicit project lifecycle (active/paused/closed) with paused->resumed side effects (rescheduling check-in cadence) and a success_status on close, plus documented derived-status precedence. Add to REQUIREMENTS Projects module and IMPLEMENTATION Phase 3.

### [LOW] Board / kanban ordering has no documented concurrency-safety strategy

*plan status: `underspecified`*

- **Operately today:** Operately stores kanban ordering server-side and keeps it consistent on create/move/delete, using row-level FOR UPDATE locks for space boards to avoid lost updates under concurrency; ordering state is normalized against current items (space_sync.ex, ordering_state.ex).
- **Evidence:** OpenOKR boards store 'manual order' via `query_orderings` (IMPLEMENTATION P3-T10 line 395; UIUX §board) and rely on generic `lock_version` optimistic concurrency (TECHNICAL §612), but there is no spec for concurrent card-reorder correctness or ordering normalization against deleted/hidden items.
- **Recommendation:** Specify how manual board/list ordering is persisted and reconciled: a normalization step that drops deleted/closed ids and appends new ones, and a locking or CRDT-fractional-index strategy for concurrent reorders. Note in TECHNICAL §4 boards and the P3-T10 task.

**Ways to be superior (beyond parity):**

- _(M)_ **AI-drafted project check-ins and retrospectives grounded in real activity** - Because every mutation is captured (audit_events/activities) and content is embeddable (pgvector), the copilot can auto-draft the weekly check-in ('what changed, what's at risk') and the closing retrospective from the actual task/milestone/comment deltas, then the champion edits and publishes. Operately's check-ins and retros are entirely hand-written. _Why:_ Operately has the cadence and health model but no AI drafting; grounding drafts in real diffs removes 'status-meeting optimism' and cuts the reporting burden that makes check-ins lapse.
- _(M)_ **Health that is computed from data, not self-reported** - Blend the human-reported check-in health with an engine-derived signal (overdue tasks/milestones, done_ratio trend, KR/KPI RAG of linked objectives) and surface divergence ('reported on_track but 3 milestones slipped'). Store both. _Why:_ Operately's project health is purely a manual dropdown on the check-in; a data-derived cross-check catches optimistic reporting and leverages the scoring engine + OKR/KPI links the plan already has.
- _(L)_ **One work-map with RLS-safe, tenant-isolated derived status for goals+projects+tasks** - Ship the unified hierarchy view the plan lacks, with a single derived-status contract recomputed by job, keyset-paginated and virtualized to the plan's 1M-item budget, and enforced by Row Level Security so cross-tenant leakage is impossible at the DB layer. _Why:_ Operately's WorkMap is powerful but its isolation is app-layer; delivering the same composition on RLS + the plan's scale budgets beats it on both security and scale.
- _(S)_ **Reviewer acknowledgement + SLA as an inbox/notification SLA, with escalation** - Model reviewer acknowledgement of check-ins with a due window; when unacknowledged, escalate via the notification spine and show an SLA badge. Tie 'outdated' + 'unreviewed' into the command palette and dashboards. _Why:_ Operately tracks acknowledged_by/at but has no escalation/SLA; adding accountability SLAs turns the operating rhythm into an enforceable process.

## 3. Spaces (Groups) & the Access-Control / Permissions / Bindings model

### [CRITICAL] No object-level authorization backstop — RLS is workspace-scoped only, and there is no single authorized-read chokepoint

*plan status: `underspecified`*

- **Operately today:** Operately enforces per-object (space/project/goal) read authorization in-query at a single chokepoint (Operately.Repo.Getter.get/2, used by every schema) plus Access.Filters for list endpoints, joining the access graph and dropping unauthorized rows automatically. Forbidden vs not-found is deliberately collapsed to avoid existence leaks.
- **Evidence:** TECHNICAL-PLAN §8.1 layered authz table: layer 1 RLS policy is only `USING (workspace_id = current_setting('app.workspace_id'))`; layer 2 is `can(user,permission,context)` via tRPC middleware. TECHNICAL-PLAN §2: 'RLS enforces workspace isolation; the core permission layer enforces role/permission checks'. Nothing scopes reads to project/objective membership at the DB. Operately: app/lib/operately/repo/getter.ex, app/lib/operately/access/filters.ex.
- **Recommendation:** State explicitly that within-workspace object visibility (private projects, confidential objectives, shared work packages) is NOT covered by RLS and MUST route through one mandatory authorized-fetch helper in packages/core (a Getter analog) plus a composable access-filter for every list query, so a forgotten check fails closed. Optionally add object-scoped RLS predicates keyed on a per-request principal GUC. Add a CI/lint rule that bare reads of authz-scoped tables outside the helper fail the build, mirroring the existing 'RLS-or-fail' migration grep.

### [HIGH] Binary project.public flag — no graded privacy tiering (internal/confidential/secret) or derived privacy label

*plan status: `underspecified`*

- **Operately today:** Operately derives a 4-tier privacy label (public / internal / confidential / secret) for every space/project/goal purely from the access levels granted to the anonymous, company-standard, and space-standard groups, and exposes public/company/space access levels in the UI editor (AccessLevels.calc_privacy, access_levels_loader.ex).
- **Evidence:** DATABASE §4.2 / TECHNICAL-PLAN §4.2: `projects.public bool` is the only visibility control; `queries.visibility` is private/public. No 'workspace-internal but not this project' vs 'confidential' vs 'secret' gradation and no derived privacy label. RBAC builtins (anonymous, non_member) can express public and internal, but there is no confidential/secret tier and no computed label.
- **Recommendation:** Replace `projects.public bool` (and add for objectives/spaces) with a privacy label derived from the access granted to anonymous / workspace-member / non-member principals, and expose a 3-lever access editor (public / workspace / members) like Operately. Document the mapping onto the anonymous+non_member pseudo-roles in TECHNICAL-PLAN §4.1/§4.2 so the label is derived, not a stored boolean.

### [HIGH] Suspended/deactivated-user exclusion is not specified in the authorization path

*plan status: `missing`*

- **Operately today:** Operately filters suspended people out of EVERY access computation (Fetch, Filters, Getter.base_query all add `where is_nil(p.suspended_at)`; Access.GroupMembership and Groups.Member scope their person assoc to suspended_at IS NULL, and Member also excludes type='ai'). - **Evidence:** OpenOKR has `users.status` (TECHNICAL-PLAN §4.1) but neither §8.1 nor §4.1 states that can() and every membership/role/group join must exclude suspended users. - **Recommendation:** Add a hard rule in TECHNICAL-PLAN §8.1: can() and all membership/role/group joins must exclude suspended/inactive users, enforced centrally in the authorized-fetch helper, with an integration test asserting a suspended member loses read/write everywhere (mirror Operately's suspended-access feature tests). Also decide handling of AI/service principals (Operately excludes type='ai' from member joins).

### [MEDIUM] Authorization for polymorphic sub-resources (comments/attachments/check-ins) has no defined inheritance mechanism

*plan status: `underspecified`*

- **Operately today:** Every Operately sub-resource inherits its parent's access context via `has_one :access_context, through:`, so messages, tasks, check-ins, resource-hub docs and activities need no bindings of their own; a new sub-resource type requires zero new authz wiring, and activities get a context stamped by ContextAutoAssigner (raising on unknown actions).
- **Evidence:** OpenOKR comments/reactions/notifications/activities are polymorphic on `subject_type`+`subject_id` (DATABASE §4.6) and check_ins are polymorphic on objective/key_result (TECHNICAL-PLAN §4.12.5). ### [MEDIUM] No workspace-level read-only / freeze overlay

*plan status: `missing`*

### [MEDIUM] Effective-permission composition across multiple grant paths is unspecified

*plan status: `underspecified`*

## 12. Rich text: ProseMirror content model, rich_content, markdown, prosemirror2html

### [CRITICAL] Markdown-as-storage contradicts the plan's own co-edit-ready mandate and loses the stable inline node IDs Operately depends on

*plan status: `underspecified`*

- **Operately today:** ProseMirror JSON is the single source of truth in JSONB; mention nodes carry attrs.id and blob nodes carry attrs.id/src.id — these IDs are load-bearing for notifications, attachment linking, and cross-company import rewriting (RichContent.find_mentioned_ids, RichContent.Blob.find_ids, company_transfers/import/rich_text_rewriter.ex).
- **Evidence:** PLAN.md §7 rule 1: 'Document-like content is stored as structured JSON with a version column, never as opaque blobs' — but DATABASE.md line 19, TECHNICAL-PLAN.md §4 (line 48) and §4.6/§4.4.1 all state rich text is 'Markdown stored with a format tag + version int (co-edit-ready)'. Markdown is not structured JSON and is a poor Yjs/CRDT target. Operately: app/lib/operately/rich_content.ex + rich_text_rewriter.ex rely on node-level attrs.id.
- **Recommendation:** Resolve the contradiction in favor of storing canonical structured JSON (ProseMirror/TipTap doc) as the source of truth with a version int, exactly as PLAN.md §7 already requires; demote Markdown to a derived, lossy view (import/export + AI authoring bridge). Update DATABASE.md line 19 and TECHNICAL-PLAN.md §4/§4.6 accordingly, and define stable node-id semantics for mentions and attachments so notification-diffing and import ref-rewrite (TECHNICAL-PLAN §7 step 5) have real IDs to rewrite.

### [HIGH] TipTap editor + Markdown storage is a lossy round-trip on every save/load

*plan status: `underspecified`*

- **Operately today:** Operately keeps TipTap JSON verbatim and only derives markdown one-way; it explicitly documents that JSON→MD→JSON is lossy (links, code marks, highlights, blob metadata like filesize/filetype/status are dropped) and that FromMarkdown is NOT the inverse of MD.RichText.
- **Evidence:** UIUX-PLAN.md line 76 specifies 'One editor everywhere (TipTap-class, Markdown storage)'. A TipTap editor's native model is JSON; storing markdown forces JSON→MD on save and MD→JSON on load. Operately's from_markdown.ex is a deliberately minimal grammar (headings, paragraphs, lists, bold, @mentions only) — round-tripping through it corrupts highlights, code marks, nested marks, tables, and attachment attrs.
- **Recommendation:** Either (a) store the editor's JSON directly (preferred, matches PLAN §7), or (b) if markdown is kept, restrict the editor's feature set to what round-trips losslessly in your markdown flavor and explicitly enumerate the lossy node/mark types in TECHNICAL-PLAN. Add golden-master round-trip tests (Operately has ~1000 lines of MD render tests) to catch silent corruption.

### [HIGH] No HTML sanitization / XSS strategy for rendering stored markdown

*plan status: `missing`*

- **Operately today:** Operately stores JSON and renders node-by-node; prosemirror2html.ex deliberately does not HTML-escape because authors are authenticated and content is never raw HTML — a safety property that comes from the JSON model, not from escaping.
- **Evidence:** Security posture (PLAN.md §6 / digest) lists strict CSP, Zod, SSRF checks — but nothing about markdown sanitization. Markdown permits embedded raw HTML, and the importer does HTML→Markdown conversion of untrusted legacy content (TECHNICAL-PLAN.md line 492, IMPLEMENTATION-PLAN.md line 745). Rendering that markdown to HTML for the app and for email (needed but unspecified) is a stored-XSS vector across an RLS multi-tenant surface.
- **Recommendation:** Add an explicit rich-text rendering pipeline section: forbid raw HTML passthrough in the markdown renderer, sanitize output (allowlist renderer / DOMPurify-equivalent) at every render surface (app read view, email, notifications, exports), and treat imported HTML→Markdown as untrusted. State that CSP is defense-in-depth, not the primary control. Add this to TECHNICAL-PLAN security and to P2/P3 tasks.

### [HIGH] Mention and attachment embedding syntax in markdown is undefined

*plan status: `underspecified`*

- **Operately today:** Mentions are ShortUuid-encoded IDs with a slugged human label (id_with_comments), and blob src appears in three encodings (attrs.id, attrs.src.id, '/blobs/<uuid>'); both notification-diffing and import rewriting parse these reliably.
- **Evidence:** UIUX-PLAN.md line 76 promises '@mentions, ##1234 WP autolink, paste-to-upload attachments' and TECHNICAL-PLAN.md line 417 promises a 'reference-rewrite pass' remapping mentions/attachment refs — but no doc defines how a person-id or attachment-id is embedded in the stored markdown, nor a canonical parser to extract them back out. Import ID rewriting and mention notifications both require this.
- **Recommendation:** Specify the exact canonical token form for @mention (embedding user id + label), ##id WP link, and inline attachment reference in the stored content, plus the extraction function used by (1) mention→notification, (2) import ref-rewrite, (3) search indexing. ### [MEDIUM] Inline attachment UX (optimistic placeholder, live upload progress, submit-gating, failure rollback, preview modal) not specified

*plan status: `underspecified`*

### [MEDIUM] Stale-mention notification correctness on edit not addressed

*plan status: `missing`*

- **Evidence:** IMPLEMENTATION-PLAN.md P3-T16/T17 cover 'mention parsing' and 'mention→notification' but say nothing about what happens when a mention is added or removed on a subsequent edit. ### [LOW] Draft autosave lacks base-content invalidation semantics

*plan status: `underspecified`*

### [LOW] Excerpt/summary generation for emails, inbox previews, and feed summaries not specified

## 15. Backend integrity architecture: Operations pattern, state machines, pub/sub, schema/repo, and multi-tenant isolation

### [CRITICAL] No transactional outbox — adapter-based JobQueue/Realtime/Mailer breaks write↔notify/audit atomicity, and the serverless tier makes it impossible

*plan status: `missing`*

- **Operately today:** Notification/email dispatch is enqueued as an Oban job INSIDE the operation's Ecto.Multi transaction (Oban shares Operately.Repo), so a notification is scheduled iff the business write commits — a true transactional outbox (app/lib/operately/activities.ex enqueue_notification_dispatch via Multi.run + Oban.insert; config/config.exs Oban repo: Operately.Repo).
- **Evidence:** PLAN.md §7 rule 2 ('all writes go through one server mutation layer') is framed only for co-edit, not atomicity; §8 says 'Drizzle migrations… committed with the feature'; TECHNICAL-PLAN §5 JobQueue port = pg-boss (container) / Inngest (serverless), Realtime = WS/LISTEN-NOTIFY / Supabase, Mailer = SMTP / Resend; IMPLEMENTATION-PLAN P2-T06 says notify 'enqueues a mail' and P2-T03 recordAudit is a separate service call. Nothing ties the domain write, audit_events insert, notification insert, and job enqueue into one DB transaction. On RUNTIME=serverless the JobQueue driver is Inngest (an external HTTP call) and Realtime is Supabase — enqueue can NEVER share the Postgres transaction, so notifications/emails can fire for a rolled-back write or be lost for a committed one. vs Operately app/lib/operately/operations/goal_creation.ex + activities.ex.
- **Recommendation:** Add a first-class DB `outbox` table. Define the write path as: open a Drizzle transaction, mutate domain rows + insert audit + insert notifications + insert an outbox row, commit. A separate relay process drains outbox rows and calls JobQueue/Realtime/Mailer AFTER commit (at-least-once). Make 'transactional enqueue' part of the JobQueue port contract; document that the Inngest/Supabase serverless drivers MUST go through the outbox relay, never a direct HTTP enqueue on the write path. Cite in PLAN.md §7/§8 and TECHNICAL-PLAN §5.

### [HIGH] No uniform transactional Operations/command pattern — each Server Action/tRPC procedure hand-rolls the write, risking non-atomic multi-table writes and missed audit/activity/notification

*plan status: `underspecified`*

- **Operately today:** Every domain write is one self-contained Operation module: an Ecto.Multi pipeline (validate → build changesets → action → record Activity → enqueue notification → commit) run atomically and unwrapped via Repo.extract_result. ~91 operation modules + composable sub-ops (subscription_list.ex, Access.insert_binding) make new writes near-mechanical and auditable (app/lib/operately/operations/*).
- **Evidence:** TECHNICAL-PLAN §1 lists packages/core 'Domain services' and §14 lists tRPC routers with CRUD verbs, but no doc defines a mandatory write pipeline that co-locates validation, mutation of multiple tables, audit, activity, and notification in a single transaction. IMPLEMENTATION-PLAN treats can() (P2-T02), recordAudit (P2-T03), and notify (P2-T06) as independent services a procedure calls ad hoc. A strategy write like 'create objective + KRs + alignment pointer + activity' (DATABASE §18) has no atomic-pipeline home. Consequence: a procedure that forgets recordAudit/notify, or that writes objective then KRs in two round-trips, is a silent correctness/audit hole.
- **Recommendation:** Specify an `Operation`/command abstraction in packages/core: each write is a module that receives actor+input, runs inside one Drizzle transaction, and returns a typed result; audit + activity + outbox enqueue are structural steps of the pipeline, not optional calls. Add a lint/CI check that mutating tRPC procedures go through an Operation. Add a P2 task and a §-in TECHNICAL-PLAN mirroring Operately's Operations pattern.

### [HIGH] Object-level authorization is app-code-only; RLS isolates only the workspace, so a forgotten filter leaks cross-project/private data within a tenant

*plan status: `underspecified`*

- **Operately today:** Authorization is data resolved by a single query: Repo.Getter joins resource→access_context→bindings→group→memberships→person and returns the row only if the requester has the required access level, else {:error, :not_found} (no existence oracle). Enforced at the read layer for every schema, not per-endpoint (app/lib/operately/repo/getter.ex).
- **Evidence:** TECHNICAL-PLAN §8.1 RLS policy is `USING (workspace_id = current_setting('app.workspace_id'))` — tenant-level only; the same table says object/role checks live in layer 2 `can()` in core. §2 has projects/private projects, `queries.visibility private/public`, per-object sharing (memberships.shared_entity), kpi_shares, objective_shares. But every list/read must REMEMBER to add the access filter in app code; there is no query-layer access enforcement. This is precisely the 'isolation is app-code only' weakness the plan criticizes OpenProject for (TECHNICAL-PLAN §8.3), just at project/object grain instead of tenant grain. A single missing WHERE leaks another team's private objectives inside the same workspace.
- **Recommendation:** Push object visibility into the database or a mandatory access-aware query builder: either (a) extend RLS with a per-request GUC of the acting user id + a membership/sharing join in the policy, or (b) a Drizzle 'getter' wrapper that every read goes through, applying the access join and returning not-found on forbidden. Adopt not-found-on-forbidden as a documented invariant. Amend TECHNICAL-PLAN §8.1/§8.3 and add a task.

### [HIGH] Effective-permission resolution across multiple grants is unspecified (no 'highest-access-wins' union, no read-time suspension revocation)

*plan status: `underspecified`*

- **Operately today:** get_for_person groups by resource.id AND person.id then selects max(access_level) across ALL of the person's overlapping group memberships (company-standard + space-full + champion/reviewer), so multiple grants correctly union to the highest; base_query also filters is_nil(suspended_at) so suspension revokes access at read time (app/lib/operately/repo/getter.ex).
- **Evidence:** IMPLEMENTATION-PLAN P2-T02 defines can() with 'group role inheritance' but says nothing about what happens when a user has several conflicting grants (direct membership + group + object share + kpi_shares scope). PLAN.md §6 and TECHNICAL-PLAN §4.1 model roles/permissions/sharing but never state the resolution rule. Risk: an implementer picks the first matching grant (possibly the lowest) or double-counts rows. There is also no stated mechanism for a suspended/deactivated member to lose access at read time (users.status has `locked` but no revocation semantics tied to reads).
- **Recommendation:** Specify in P2-T02 and TECHNICAL-PLAN §6/§8: effective access = MAX over all grants (direct role, group-inherited role, object share, strategy-scope share); a suspended/locked/inactive membership yields no access at read time, enforced in the same query/policy as authorization, not only at login. Add a permission-matrix test with overlapping grants.

### [MEDIUM] Activity/audit content is free-form jsonb — not validated, versioned, or snapshotted; feed breaks or crashes after referenced records change/delete

## 17. Testing, CI, and quality engineering

### [HIGH] No E2E/integration DB-isolation-and-reset strategy under RLS — the foundational hard problem is unaddressed

*plan status: `missing`*

- **Operately today:** Transactional per-test isolation shared across the HTTP/browser/CLI boundary via SQL sandbox metadata; CI-vs-local pool/timeout tuning.
- **Evidence:** TECHNICAL-PLAN §10 lists 'Integration (Vitest + real Postgres)' and 'E2E (Playwright): one happy path per P0 feature' but says NOTHING about how tests isolate/reset DB state, seed per-test data, or set the app.workspace_id GUC per test. IMPLEMENTATION-PLAN P1-T03 only proves RLS with a two-workspace test. Operately's hard-won detail: every test runs inside Ecto.Adapters.SQL.Sandbox, and Wallaby/CLI/MCP e2e all JOIN the same transaction via sandbox metadata so the browser and out-of-process requests see uncommitted, auto-rolled-back test data (cli_e2e_case.ex, mcp_e2e_case.ex, config/test.exs pool tuning).
- **Recommendation:** Add a §10 subsection choosing an isolation model that survives the Playwright cross-connection boundary (per-worker database or schema + TRUNCATE-between-tests, or a template-DB fast reset) AND a way to set the app.workspace_id GUC per test/worker. ## Appendix B - Strategic deep-dive top recommendations

Full analysis is in OPERATELY-COMPARISON.md; these are the raw top-line recommendations per theme.

### Theme: The OpenOKR plan is a competent, disciplined greenfield spec, but it proposes rebuilding from zero a system whose hard parts Operately has already shipped and battle-tested across ...

- Make an explicit, written build-vs-fork decision measured against Operately (not OpenProject): forking Operately's Elixir/Phoenix + TurboUI codebase inherits the access model, ~300 typed RPC endpoints, 515 components, 800+ tests, an MCP+OAuth server and AI agents on day one — the plan never evaluated this and it likely dominates greenfield on every axis except a hard Next.js/TS mandate.
- Add real sizing and a critical path: 109 unestimated, unequal, strictly-sequential tasks hide a multi-engineer-month-to-year effort; estimate each task, split the mega-tasks (P3-T05/T08/T10, P4-T04/T08, P5-T06), and re-baseline — the honest total will likely change the strategic decision.
- Drop the RLS-on-every-table mandate in favor of Operately's proven app-level authorization (context/binding/group query filters + can()); RLS via a session GUC adds real cost, still needs an app layer, and is unsafe under the serverless connection pooler the plan also depends on.
- Pick ONE runtime for v1 (container + Postgres-backed job queue, mirroring Operately's Oban) and stop requiring dual container/serverless parity and dual-profile CI — this removes a permanent tax that multiplies the cost of nearly every stateful feature.
- Narrow v1 scope hard: cut the OpenProject importer entirely (replace with generic CSV/XLSX), defer the automatic scheduling engine, Gantt propagation, backlogs, meetings, wiki, and autonomous AI to post-launch, and re-sequence so the OKR/strategy pillar (the product's namesake) ships as an early end-to-end slice instead of behind 34 work-management tasks.
- Turn the two flagged 'engines' into timeboxed research spikes with written scenario matrices and reduced-scope fallbacks, port Operately's already-validated goal status/progress logic as the reference spec, and add a risk register with kill/simplify criteria and a human-review throughput assumption to the execution guide.

### Theme: OpenOKR is scoped as capability *parity* with OpenProject + FlowyTeam (work packages, custom fields, configurable types/statuses/workflows, a JSON query DSL, Gantt, backlogs)...

- Reframe the plan's north star from 'parity with OpenProject + FlowyTeam' to 'the opinionated default operating rhythm ships first, configuration is the optional floor beneath it.' Lead every surface (onboarding, home screen, docs) with the single opinionated OKR + weekly-check-in + champion/reviewer path; gate custom fields / configurable workflows / the query DSL behind an explicit advanced mode. Breadth is not the differentiator against Operately — installed opinion is.
- Promote three subsystems from P1/P2 fast-follow into the core strategy pillar because together they ARE the operating system: (a) a Cadence engine that auto-computes the next check-in due date with an opinionated default (weekly), porting the on-time tolerance from Operately's time.ex; (b) a required champion/reviewer accountability contract with a mandatory reviewer-acknowledgement loop on every check-in/update; (c) a per-person 'Review / My Assignments' inbox that derives obligations (check-ins due, acknowledgements owed, tasks/milestones due) from cadence + role and ranks them overdue-first.
- Make progress narrative-first and enforced: model the check-in as a structured social object that snapshots KR/target values, requires a written narrative, and carries a small fixed status vocabulary; derive a goal's health from its latest check-in; and compute an 'outdated/stale' state from the cadence that overrides self-reported health everywhere. This gives accountability teeth that no amount of configurability provides.
- Ship the Work Map as the opinionated home screen — one company-wide goal->project->task tree with unified status/next-step/progress/owner rollup spanning both pillars (mirroring Operately's single WorkMapItem contract) — rather than expecting users to assemble equivalent views from saved queries and boards.
- Leapfrog Operately on AI by making the differentiator autonomous, accountable AI teammates (agents that are Person-like members, can own/contribute to goals, run on the operating cadence to plan and execute, and post check-ins/comments into the same feeds and review inbox), keeping the MCP/copilot/BYO-key tool layer as support rather than the headline; and separate the append-only compliance audit log from a rich, typed, per-event social activity feed with retrospectives baked into the goal/project close lifecycle.

### Theme: Operately ships a battle-tested, relationship-based access engine (access_contexts + access_bindings + access_groups) with a single-transaction Operations pattern that makes author...

- Keep RLS only as the tenant-isolation FLOOR and add a relationship/binding authorization layer on top (port Operately's access_context+access_binding+access_group, or use OpenFGA/SpiceDB) enforced through a single core can() shared by tRPC, REST, and MCP — do not ship pure RBAC, which cannot express Operately's per-object/space/anonymous/champion sharing and is a costly retrofit.
- Implement RLS defensively: SET LOCAL app.workspace_id inside every transaction, verify PgBouncer/serverless pooling resets it per transaction, deny BYPASSRLS to the app role, and add a CI test that an unset-GUC connection returns zero rows from every business table (the plan's dual serverless+container runtime doubles this risk).
- Fold the audit record into the SAME DB transaction as the mutation (Operately's insert_sync pattern) and drive async side-effects via a transactional outbox — never a fire-and-forget queue call — then beat Operately by adding tamper-evidence (per-tenant hash chain / signed events) and a typed, Zod-validated event schema instead of a free-form JSON blob.
- Bound every agent/MCP/tool call to a concrete human principal with NO ambient authority, run authz + Zod validation in the shared tool-registry layer (so one-def-three-surfaces cannot diverge), classify tools read/write/destructive, and gate destructive autonomous actions behind elevated scope + human-in-the-loop; treat all RAG/retrieved/model output as untrusted (prompt injection) and SSRF-allowlist BYO/local model egress.
- Copy Operately's shipped MCP OAuth 2.1 hardening verbatim rather than re-deriving it: mandatory PKCE-S256, resource-indicator (audience) binding checked on issue and every token use, short access-token TTL, refresh rotation with reuse-detection that revokes the whole grant lineage, hashed tokens at rest, origin validation, and grant revocation on membership/role change.
- Keep authorization checks before a single-transaction write path (Operately's Action pipeline -> Ecto.Multi is the template): load access-scoped entities, check_permissions, then one atomic transaction for state + ACL rows + audit; add integrity tests asserting a mutation without its audit row is impossible.
- Adopt cheap wins Operately lacks: hash session tokens at rest, ship read/write-scoped API tokens (Operately's enforce_token_access_mode), and use Zod for complete boundary validation instead of a partial hand-rolled JSON-schema subset.

### Theme: On AI & agents the OpenOKR AI-NATIVE-PLAN is a mix: BEHIND Operately on the two things that actually matter most for "AI-native" — autonomous agent execution and MCP/OAuth depth — ...

- Rewrite §5 MCP auth: drop PAT-first, specify full OAuth 2.1 + PKCE(S256) + rotating refresh tokens with reuse detection + RFC 8707 resource indicators + CIMD + consent/company-picker + ChatGPT search/fetch discovery — matching what Operately already runs (token_exchange.ex, client_metadata.ex), because the plan is materially BEHIND here.
- Add autonomous agent execution to the plan (plan/execute phases, scheduled/cron runs, sandbox mode, per-task logs) and reframe the absolute 'writes are always proposed-then-confirmed' principle into a per-mode policy — the current plan forbids the autonomous-agent category that Operately already ships (agent_worker/planning_phase/execution_phase/cron).
- Adopt agents-as-first-class-members (a Person type 'ai' + an agent-definition record with persona/instructions/provider) instead of the plan's token-scoped 'agent is the user', so agents have identity, can own/be-assigned work, and are audited in the same model as humans.
- Stop re-specifying the inbound MCP tool server as new work — Operately already has ~102 permission-checked tools with safety classifications and per-tool scopes; treat that catalog/definition/executor model as the reference to match and redirect P5-T09 effort elsewhere.
- Concentrate the plan's original investment where it genuinely leads and Operately is empty: provider abstraction (Ollama/OpenRouter/openai-compatible/local), per-user BYO keys with envelope encryption, model catalog + tier routing, cost metering + hard caps, per-feature admin governance, and pgvector RAG — this, not the MCP server, is the plan's honest path to leading on AI.
